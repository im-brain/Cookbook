# CLAUDE.md — read this first every session

This is a personal cookbook website. The full plan and progress are in `PLAN.md`.

## About the user

- New to coding. Explain every change in plain language and avoid jargon (or explain it the first time).
- Uses an **iPhone with Safari** only. Design and test for that.

## How we work

1. Work on **one step from `PLAN.md` at a time**.
2. **Plan first.** Before changing any files in the repo or committing, Claude shows a short plan: what will change, which files (including which notes in `CLAUDE.md` / `PLAN.md`), and any choices made. Then Claude waits for the user's OK. Scratch work (test scripts, trying ideas in the scratchpad) doesn't need asking first.
3. Claude writes the code and explains what changed and why, in plain words.
4. Claude checks the step in a simulated iPhone screen (Playwright, iPhone viewport) and sends the user a screenshot.
5. Claude raises the **version number** (see Lessons learned) and opens a pull request that says which version to look for. The user taps **Merge** on GitHub.
6. About a minute later the live site updates at **https://im-brain.github.io/Cookbook/**. The phone may keep an old copy for up to 10 minutes, so the user waits, fully closes the app (swipe it away) and reopens it from the icon, checks the version number at the bottom of the home screen, then tests.
7. If something is broken, fix it before starting the next step.

## Memory rule (important)

New sessions start with no memory of earlier conversations, so this file and `PLAN.md` are the memory.
**Every pull request that changes anything** (not only numbered steps) also updates the notes, in the same pull request:
- In `PLAN.md`: tick any finished checkbox, update **Current status**, and add a dated line to the **Progress log**.
- In this file: add any new decision or lesson to **Key decisions** or **Lessons learned**, and keep the version-number list current.

## Key decisions (and why)

- **Plan before doing (2026-10-31, user's request):** the user liked getting a plan before any work, so every change starts with a plan and waits for an OK (see "How we work", step 2).
- **One step per session (2026-11-08, user's choice):** each redesign phase (or fix) is done in its own new session, to save tokens. A session reads `CLAUDE.md` and `PLAN.md` first, does only the next unticked step (plan → OK → build → check → pull request), updates the notes, and stops. It reads only the parts of the proposal page it needs for that step (Artifact tool `read` with a `path`, e.g. `shots/04-recipe-light.jpg` or `demo/proto.css`).
- **Plain HTML, CSS and JavaScript.** No framework, no build tools. Simplest to learn; edit a file, see the change.
- **Recipes are stored on the phone (localStorage).** No account, database or cost. Online sync is a "maybe someday". *(Changes in redesign Phases 4–5: private Supabase sync; the phone keeps a full local copy.)*
- **Public repository + GitHub Pages.** Free Pages doesn't work for private repos. Only code is public; recipes never go in the repo.
- **Always open the cookbook from the Home Screen icon.** Safari deletes a website's saved data after ~7 days of Safari use without visiting it, but Home Screen apps are exempt. The Home Screen app and a Safari tab have **separate storage**, so recipes saved in one don't appear in the other. That's why the install step comes early, before real recipes are saved.
- **Backups:** Export a file (save it to iCloud Drive), Import it back. The reminder shows "N recipes changed since your last backup" whenever there are unbacked-up changes (risk is losing the phone, not Safari).
- **Import merges, never replaces** (user's choice): recipes missing from the phone are added, a recipe in both keeps the newer `updatedAt` (a tie keeps the phone's copy), nothing is deleted, and it asks first (`confirm`).
- **Export uses the iPhone Share menu** (`navigator.share` with a file), so the user taps Save to Files. If sharing isn't available (e.g. a computer), the file downloads instead.
- **Two kinds of recipe:** "My own" (no original) and "From somewhere else" (optional source, e.g. a link or "Grandma's card"). For the second kind, the first saved version is kept as the **original**; edits are "mine". Show "mine" by default, with **View original** and **Reset to original** (asks first).
- **Recipe fields:** title, ingredients, steps, servings, total time, tags, notes, kind, source, and (Version 30) one optional photo. *(Photos are not in `localStorage`, which holds only about 5 MB: see "Photos" below.)*
- **Ingredients and steps are entered one at a time** (user's choice after trying a big text box): one box per item, "+ Add ingredient" / "+ Add step" or the keyboard's Next key adds the next box, × removes one. Steps are numbered.
- **Editing (step 9):** the same form as "Add a recipe", filled in. The kind ("My own" / "From somewhere else") is fixed once saved, so its choice is hidden when editing; the source can still change. Reset to original replaces only `current`; notes and source stay. Delete and Reset both ask first (`confirm`). Buttons sit at the bottom of the recipe page; Delete has red text.
- **Notes** are separate from edits and shown **above the ingredients**.
- **Tags:** starter list (breakfast, lunch, dinner, dessert, quick, vegetarian) plus the user's own.
- **Own tags are not stored separately (step 10):** the offered tags = starter tags + every tag on any saved recipe (`current` or `original`). So there is no extra storage key and backups carry tags automatically. A tag nobody uses any more simply stops being offered. Tags are lower case, single-spaced, max 30 characters.
- **Search (step 11)** looks at title, ingredients and tags of "my version" only (not notes, steps or the original). Every typed word must match somewhere; case and accents are ignored. It filters live as you type; there's no separate results screen.
- **"What should I cook?" (step 12)** is a box on the home screen, not a separate screen. The filter offers only tags actually used on a saved recipe, so a filter never comes up empty. It picks from "my version" tags. No repeat of the previous pick unless it's the only choice.
- **Cooking mode (2026-10-31, grill-me interview), steps 13–15:** "🍳 Start cooking" sits under the title/tags and always cooks "my version" (hidden while viewing the original). It opens a separate cooking screen with bigger text where you tap ingredients/steps to tick them off. Ticks are in memory only and forgotten on Done cooking; leaving doesn't ask first. **No timer in the cookbook** (user's choice: they use Siri / the Clock app; a Shortcut-based "iPhone Timer" button was offered and declined). Times in steps are shown in bold instead. The screen stays awake while cooking.
- **Scaling (step 14):** − / + servings (if the recipe has servings) plus ½×, 1×, 2×, 3×; only for the cooking session, never saved; kitchen fractions (nearest ¼ or ⅓), changed numbers highlighted; the ½×–3× buttons are **kept but small** (user's choice, Version 17: − / + is the main control, and the × buttons still let recipes without servings be scaled); only the amount at the **start** of an ingredient line is scaled (user's choice: "2 (14 oz) cans" → "3 (14 oz) cans", "Juice of 1 lemon" unchanged); amounts of 10 or more are rounded to whole numbers (user's choice); words aren't changed ("1 cups").
- **Converter (step 15):** on the cooking screen only. **US measures** (cup 240 ml, tbsp 15 ml, tsp 5 ml); volumes, weights, °F ↔ °C, and cups ↔ grams for a built-in list of 12 common ingredients (see `PLAN.md`).
- **Import a recipe (2026-11-01, grill-me interview), steps 16–17:** step 16 smart paste (on the phone only), step 17 from a link (free Cloudflare Worker; paste is the fallback when a site blocks it). A "✨ Fill in automatically" box at the top of the **New recipe** form only (hidden when editing), with 📋 Paste and Fill in. It only **fills the form**: the user reviews, then taps Save. It sets kind "From somewhere else" and puts a found link in Source. Asks first if the form already has content; notes and tags are never replaced. No headings → guess + "Please check the ingredients and steps." Step 17: website description ignored; categories → tags (matching ones ticked, new ones as **unticked** chips); warn if a recipe with that link as source exists (button to open it). The user creates the Cloudflare account; the Worker's code lives in `worker/` (no secrets) and only answers the cookbook's site, returning only recipe parts. **AI upgrade: later**, only if free import often fails.

## Lessons learned

- **This Week code map (Version 31):** `js/plan.js` (loaded after `js/ingredients.js`) = dates (`weekStartOf`, `addDays`, `weekLabel`, all through UTC midday so clock changes can't shift a day) and plan changes that return a **new** plan (`addEntry`, `changeEntry`, `removeEntry`, `moveDay`, `moveSide`, `reuseWeek`, `mergePlans`, `cleanPlan`). `js/plan-ui.js` (loaded after `app.js`) = `loadPlan()` (null if damaged: **never write then**) / `savePlan()`, `renderPlan()`, the three bottom sheets (`#plan-sheet`, `#plan-menu`, `#plan-reuse-sheet`, class `sheet-backdrop`/`sheet`; `body.sheet-open` stops page scrolling). `app.js`: `planScreen`, `planTab`, `backToPlan` (the recipe page's Back returns to This Week when it was opened from there), backup format 4 and import. Node checks: `node tests/plan.test.js` (60). Playwright: fake the date with `page.clock.setFixedTime(new Date("2026-11-08T12:00:00"))`.
- **Second device and the move (Version 33, found when the user set up the iPad):** the six-step "Move my recipes" is per device (`cookbook.move` is on each device, so every new device must sign in and finish it). On a device that already holds some of the same recipes (same ids) as the cloud, Upload finds differences: those with a part changed on both sides become **conflicts** (the "Changed on two devices" box on the Cookbook screen), the rest wait to be sent. Fixes: (1) `verifyMove` now returns `differentDetails` (which parts differ: title, ingredients, … plus `kind`, `dates`, "deleted here only"/"deleted in the cloud only", or "formatting only") and `waitingDetails` (title + "not sent yet" / "changed since it was last sent"), and the "Not finished" message uses them and says what to do next (conflicts → open the Cookbook tab first; otherwise Upload then Verify). (2) `withMoveBusy` redraws the conflict box after every step (it used to appear only after reopening the app, because the steps call `syncNow` directly, not `runSync`). (3) **"Make this device match the cloud"** (`matchCloud(env, dryRun)` in `js/sync.js`, button `#move-match-button` in the move card, hidden once the move is finished): replaces this device's copy of every recipe the cloud already has with the cloud's copy (also its "Recently deleted" state), drops open choices for them, keeps recipes only on this device (the next Upload sends them); it asks first (counts shown) and needs step 1 satisfied. After matching, step 1 counts as done through `moveState().matched` (a backup made before matching holds what was there before; without this the matched recipes would count as "changed since your backup" and block Upload). Node checks: `tests/sync.test.js` (84).
- **Plan sync code map (Version 32):** `js/plan-sync.js` (after `js/sync.js`; works in Node: `node tests/plan-sync.test.js`, 37 checks with two pretend phones and a pretend cloud) has `syncPlan(env)`, `planPendingCount(env)`, `toPlanRow` / `fromPlanRow`; `js/auth.js` has `cloud.pullPlan / fetchPlanRow / insertPlan / updatePlan / purgeOldPlan`; `js/sync-ui.js` has `planSyncEnv()` and `planChanged()`, and `runSync()` calls `syncPlan` after `syncNow`; `js/plan-ui.js` has `writePlan` (quiet save, used by the engine) and `savePlan` (= `writePlan` + `planChanged()`; use this one for anything the person does). A screen redraw after a sync is skipped while a bottom sheet is open. **Testing screens with two devices:** in Playwright, route `**/vendor/supabase.js*` to a fake `window.supabase.createClient` whose query builder calls a Node function given to every page with `page.exposeFunction`, so both pretend devices share one pretend cloud; set `cookbook.move` to `{userId:"u1",uploaded:true,verified:true,done:true}` so sync is on.
- **Shopping (Version 34, Phase 8 Part A; user OK'd the A/B split and standard aisles on 2026-11-09):** a fourth tab **Shopping**. The list is **never stored**: it is worked out again from the plan (`cookbook.plan`) and the recipes' structured ingredients each time. Only the person's choices are stored, under **`cookbook.shopping` (never rename)** = `{ weeks: { "<Monday>": { seen, ticks, more, extras } }, pantry: [names], aisles: { key: aisle } }`. One row per ingredient **name** (`shopKey`: lower case, last word made singular); amounts add up per kind of measure: volume (kept in ml), weight (kept in g) and count per unit+package size; US units show as cups/tbsp/tsp and oz/lb, but if every source was metric it shows ml/liters and g/kg. A range uses its **upper** amount; each recipe is scaled by planned servings ÷ recipe servings (1 if either is missing); the package size never scales. Cups ↔ grams are merged only for the converter's 12 ingredients (`SHOP_GRAMS_PER_CUP`). Two kinds of measure that can't be merged (e.g. cloves + head, or cups + grams of tofu) show as "a + b" under **Needs a look**, as do lines the reader marked `please-check`. A line with no amount is absorbed into a measured row of the same name, else shown as "as written" (`writtenName` strips "to taste", "a pinch of"…). Ticks remember what was needed (`bases` per kind). **More needed** = a ticked item now needs more of any kind: the tick is removed and `more[key].was` keeps the old text; **less** stays ticked. **New** = not in `seen` (the first look at a week with items marks everything seen, so nothing is New then); "Got it" marks all seen. **No longer needed** = in `seen`/`ticks` but not on the list now and not in the pantry; "Remove" forgets it. Aisles come from `AISLE_WORDS` (first match wins; unknown = Other) unless the person chose one. Backup **format 5** adds `shopping` (left out while empty); import adds missing extras, pantry items, aisle choices and whole weeks, the phone's choices win. **Part B (Version 36)** syncs this (see Shopping sync). Code map: `js/shopping.js` (loaded after `js/plan.js`; works in Node: `node tests/shopping.test.js`, 58 checks) and `js/shopping-ui.js` (loaded after `js/plan-ui.js`; `loadShopping()` returns null if damaged: **never write then**; `writeShopping`, `renderShop`, the ••• sheet `#shop-sheet`). Playwright: fake the date with `page.clock.setFixedTime`, put recipes and a plan in localStorage, open `#tab-shop`. **Look (Version 35, user's request: "see more in the view"):** each item is one ~40px line (name, tiny `.shop-from` meals that cut off with …, amount) instead of two; this is a little under the usual 48px tap size on purpose. **The tab always opens on the current week** (no special Sunday rule). **Gotcha:** a CSS `display: grid` list needs `grid-template-columns: minmax(0, 1fr)`, or one long line makes the whole column wider than the screen and pushes the ••• buttons off the edge. In Playwright, `page.click` kept re-scrolling in a loop on these rows; scroll the row to the middle and use `page.mouse.click` at its centre.

Reduce Motion (`prefers-reduced-motion`) switches tilting off in the script and uses instant scrolling.
- **Testing gotcha:** with `file://` pages, `localStorage` didn't reliably survive `page.reload()` in Playwright. Serve the site (`python3 -m http.server 8765` in the repo, scratchpad test script opens `http://localhost:8765/index.html`) for tests that reload.
- **Ingredients code (Version 26):** `js/ingredients.js` (plain script, loaded **before** `cookbook-views.js` and `app.js`) holds `AMOUNT`, `LEADING_AMOUNT`, `amountToNumber`, `readAmount`, `kitchenNumber` and `isSectionHeading` (moved from `app.js`), plus `parseIngredient(line)` (never throws), `parseIngredients(lines)`, `ingredientText(x)` / `ingredientTexts(list)` (work for records and old plain lines), `cleanIngredient` / `cleanIngredientList` (rebuild from saved or imported data in a fixed field order, so fingerprints match after a backup round trip), `upgradeIngredients(part)` and `scaleIngredient(ingredient, factor)` → `{ before, scaled, rest }` or `null`. In `app.js`: `loadRecipes()` converts old lines in memory (so every screen sees records), `convertSavedIngredients()` saves them once at start-up, `recipeFromForm()` runs `parseIngredients`, and `fillList` returns true when it showed any "Check" tag (the hint `#view-check-hint` then appears). The file also works in Node: `node tests/ingredients.test.js` (116 checks with made-up lines). Add a row to its table when a line is read wrongly.
- Reader details: units are stored by one standard name (`cup`, `tbsp`, `tsp`, `oz`, `lb`, `g`, `kg`, `ml`, `l`, `fl oz`, `can`, ...; a capital `T` is a tablespoon, a small `t` a teaspoon). A line is `please-check` when there is no ingredient after the amount, a second number outside brackets ("1 cup or 120 g flour"), a number that isn't followed by a space or letter ("12-inch tortillas"), a huge amount, or it's over 100 characters. Numbers in brackets ("1 cup flour (120 g)") are fine.
- Testing gotcha: on the cooking screen only ingredient lines have `.cook-text` (headings don't), so list positions in a test shift after a heading. In Cover Flow view `#recipe-list` is hidden, so test search with `matchesSearch(recipe, words)` instead.
- **Cover Flow slider (Version 25, user's request):** the slider sits **under the covers, above the caption**, and the caption has a fixed height (title always reserves two lines), so nothing moves when the recipe changes. The slider is continuous (`min 0`, `max N-1`, `step any`, value = `scrollLeft / itemWidth`), follows the covers while you swipe, and while your finger is on it (`flowDragging`, `.flow-track.dragging` = `scroll-snap-type: none`) it sets `scrollLeft` directly; on release it glides to the nearest recipe. The caption only redraws when the middle recipe changes (`flowShownId`). Covers: the middle one is full size, its neighbours tilt 62° beside it, and all further ones are squeezed 16% of a cover apart like page edges (`flowTilt`). `.flow-item` has `pointer-events: none` and only the `.cover` can be tapped; the arrows have `z-index: 2000` because covers use up to 1000 (covers once sat on top of the arrows). The general `input:focus` outline is switched off for the slider (keyboard users still get `:focus-visible`).
- **Ingredient editor (Version 27, Phase 3 Part B):** each ingredient `<textarea>` in the form carries `box.ingredient` (its record), trusted only while its `text` equals the box's trimmed value; otherwise the line is read again with `parseIngredient`. `ingredientOfBox(box)`, `readIngredients()` (what `recipeFromForm` saves), `refreshIngredientRow(row)` (the grey `.understood` strip + Check tag; hides it and ••• for headings and empty boxes), and the ••• panel (`buildIngredientPanel`, `fillIngredientPanel`, `toggleIngredientPanel`, `applyIngredientPanel`; one open at a time). `ingredientFromParts(parts)` in `js/ingredients.js` writes the line's words from the parts (plural units, "2-3", "(14 oz)", ", prep", "(optional)") and the result reads back the same (Node checks). `fillEditList` keeps a saved record for edits (so a ••• fix survives), plain text from paste/link import is read. Gotcha: Enter in a panel box would submit the whole form, so the list's `keydown` catches it. The rows use `flex-wrap` so the strip and panel sit under the box.
